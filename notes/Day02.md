# 2. `candidate_data_preprare.py`：数据来源与预处理

## 2.1 大规模数据的存储方式

作者首先将原始数据处理并保存为 Parquet 格式。

这里值得关注的不是 Parquet 本身，而是作者针对**大规模数据 + 需要反复运行的数据流水线**选择了更适合作为中间数据格式的存储方式。

我的实验目前只有 10k / 3k session，数据规模较小，因此暂时没有必要完全照搬这种方案；后续数据规模扩大时，可以考虑采用。

---

## 2.2 不同训练阶段的数据过滤

作者通过 `istrain` 参数控制数据处理方式：

- 使用 Valid 进行模型训练时，不过滤数据；
- 使用全量数据进行最终训练 / 测试时，过滤掉前 7 天的数据。

这里值得关注的是：

> 作者通过限制历史数据范围，在减少数据量的同时，也避免过早的历史行为对当前用户兴趣产生过大的干扰。

这既是数据预处理策略，也是一种从计算规模和数据有效性两个角度进行的控制。

---

## 2.3 Pandas 与 cuDF 的使用

发现作者同时使用 Pandas 和 cuDF：

| | Pandas | cuDF |
|---|---|---|
| 主要运行设备 | CPU | GPU（NVIDIA） |

两者承担类似的数据处理任务，但 cuDF 可以利用 GPU 加速大规模 DataFrame 操作。

同时需要注意：

> cuDF 与 NumPy / Pandas 并不是完全兼容，因此当后续需要使用 CPU 侧工具处理数据时，需要通过 `.to_pandas()` 完成转换。

---

## 2.4 用 Session 长度组织数据

此处开源项目选择了将原始事件按照 session 聚合，得到每个 session 的**事件数量**和**最早时间**。

这里真正值得关注的是：

> 作者没有让后续算法反复处理完整的二维 DataFrame，而是先记录每个 session 有多少条事件，再将具体事件展平保存。

展平时使用`np.concatenate()`将多个 session 中的数组连接成连续的长数组。

---

## 2.5 最终的数据组织方式

经过预处理后得到：

```text
train_2_v2.csv
test_2_v2.csv
```

以及：

```text
train_2_v2.npz
test_2_v2.npz
```

其中 `.npz` 中主要保存三条展平后的长数组：

```text
aids
ts
type
```

不再单独保存 `session`。

Session 的边界通过 CSV 中的 `length` 恢复，在 `past_event.py` 中可以看到作者使用 `cumsum(length)` 计算对应位置。

因此整体的数据组织方式变成：

```text
Session 1 ─┐
Session 2  ├──→ 展平后的 aids / ts / type
Session 3 ─┘
             +
          length
             ↓
      恢复每个 session 的边界
```

这种方式值得后续继续学习：

> **将原始的二维 / 表格数据转换为“长数组 + session 长度”，可以减少重复存储，并方便后续按照 session 快速切片。**

# 3. `past_event.py`：历史序列召回

## 3.1 数据预处理

开源项目选择了把训练集和测试集的历史数据进行拼接，这是因为预测本身就需要输入对应session的历史数据，并不会造成信息泄露。

## 3.2 大量循环计算的加速

作者对核心计算函数通过 Numba 对函数进行 JIT 编译。

这里值得关注的是：

> 当 Python 中存在大量简单的数值循环时，可以通过 JIT 将其编译成更接近机器执行的形式，从而减少 Python 循环本身带来的开销。

`nopython=True` 对代码类型有更严格的要求，因此并不是所有 Python 写法都能够直接使用这种模式。

---

## 3.3 分批处理 Session

作者不是一次性处理所有 session，而是每次传入约 **1024 个 session** 进行 inference。

同时根据 session 和 `length`，提取对应位置的 `df`、`aids`、`ops` 等数据。

这里的工程思路是：

> **通过分批处理控制单次计算规模，避免一次性处理过多 session。**

---

## 3.4 JIT 环境下的数据结构


`nb.typed.Dict` 是 Numba 为 JIT 编译准备的类型明确的字典结构，使字典可以参与 `nopython` 模式下的编译。

这里值得记录的是：

> 当为了加速而进入 JIT 环境后，普通 Python 数据结构也可能需要替换成适合 JIT 编译的数据结构。

---

## 3.5 历史序列召回的核心思路

作者的历史序列召回同时考虑：

- 历史行为的位置 / 时间；
- 行为类型；
- 相同商品在一个 session 中的重复行为。

整体逻辑可以概括为：

```text
历史行为
   ↓
时间 / 序列衰减
   ↓
结合行为类型权重
   ↓
相同 aid 分数累加
   ↓
按照累计分数取 TopK
```

也就是说：

> **越相关的历史行为获得越高权重，同一个商品在历史中多次出现时，其分数会进一步累加。**

---

## 3.6 时间 / 序列衰减

作者使用`np.linspace(start, stop, num)`生成不同历史位置对应的数值，再结合 `np.power()` 等操作构造最终的指数衰减权重。

值得学习的是：

> 作者没有让所有历史行为拥有相同影响，而是让不同位置的历史行为具有不同权重。

## 3.7 其他发现

通过`inference()`的输入，我们可以发现，`result_buy` 同时用于 `buy` 和 `cart`。

也就是说：

> 作者在这里复用了 `cart` 和 `buy` 的召回结果。

从实际用户行为来看，直接购买但没有加入购物车、加入购物车但没有购买都是可能发生的，因此这里更像是一种工程上的简化。

这一点可以作为后续进一步验证和优化的方向。

---

## 3.8 TopK 的高效实现

作者使用 Heap 维护候选商品的 TopK。

相比对全部候选进行排序，Heap 所需的时间复杂度更低：

| 方法 | 时间复杂度 | 特点 |
|---|---:|---|
| Heap TopK | `O(n log k)` | 只维护需要的 TopK |
| 全量 `sorted()` | `O(n log n)` | 对全部候选排序 |

这也是很值得学习的工程优化。

# 4. 今天的核心认识

今天从数据预处理一直读到了历史序列召回，主要形成了几个认识：

1. **数据规模上来后，数据存储和组织方式本身就是工程问题。**

   Parquet、cuDF、展平数组等方案，都是为了让后续流水线更适合大规模数据。

2. **推荐系统中的召回不只是算法公式。**

   实际实现还需要考虑分批处理、JIT 加速、数据结构以及 TopK 的计算效率。

3. **TopK 不一定需要完整排序。**

   当最终只需要少量高分候选时，可以使用 Heap 降低计算开销。

4. **开源代码中的实现不一定是唯一答案。**

   例如 `cart` 和 `buy` 复用同一召回结果，就是一个可以进一步思考和验证的工程选择。

下一步将继续阅读其他召回方式，比较不同召回策略分别解决什么问题，以及作者在这些策略中采用了哪些工程实现。
